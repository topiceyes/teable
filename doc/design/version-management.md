## 版本号

仓库根目录 `VERSION` 是定制产品版本的唯一来源，初始值 `1.0.0`。该版本用于构建显示、镜像标记、发布说明及部署记录。

| 类型       | 示例       | 使用条件                           |
| ---------- | ---------- | ---------------------------------- |
| 修复       | 1.0.1      | 兼容性修复、安全修复、现有功能完善 |
| 功能       | 1.1.0      | 向后兼容的新功能                   |
| 不兼容变更 | 2.0.0      | 破坏接口、数据或使用方式兼容性     |
| 预发布     | 1.0.0-rc.1 | 发布候选，仍待验收                 |

Git 正式标签使用 `custom-v1.0.0`，后续为 `custom-v1.0.1` 等，以便与 Fork 中继承的上游标签明确区分。GitHub Release 标题使用 `1.0.0`，镜像使用 `1.0.0`，生产记录同时保留镜像摘要与 Git commit。

上游根 package.json、各 workspace package.json 目前的 `1.10.0` 属于上游内部包版本，本次保留，不批量降为 1.0.0；这不会改变定制产品的 `VERSION=1.0.0`。不要运行上游 `publish:*` 来发布本定制应用，它们会改 workspace 包版本并尝试发布 npm 包。

## 分支与合并

- `main` 作为定制版稳定分支，正式发布标签仅打在已验收的提交上。
- `develop` 用于日常集成；每项改动通过功能分支和 PR 纳入。
- 功能分支默认使用 `codex/` 前缀，发布准备分支可用 `release/1.0.0`，紧急修复可用 `hotfix/1.0.1`。
- 首版使用隔离的 `codex/release-1.0.0` 工作区整理代码，通过 PR 合入稳定分支；原开发工作区及本地知识库原件保留。远程分支保护另行配置。
- 提交前检查差异，不直接把未知修改全部 `git add .`。配置实际值、凭据、备份、业务数据及个人信息不进入公开 Fork；测试证据使用合成数据。

## 首次发布范围与步骤

1. 整理第 01—18 期已有实现为可审查提交：钉钉目录及后台配置、账号绑定、业务角色、权限矩阵、字段和记录限制、实时撤权、个人查询、部署准备。需求、设计、测试证据继续保存在本地知识库并随代码管理。
2. 上传前审查源码、文档、测试日志和截图；确认适合公开仓库的内容，实际密钥及生产数据只在受控部署环境保存。
3. 审查 Fork 的 GitHub Actions。上游现有流水线会尝试使用上游镜像命名、注册表凭据及日期式 release id，不能直接当作我们的 1.0.0 发布流程；先调整发布目标与触发条件，再启用相关工作流。
4. 源码发布前完成类型检查、权限回归、内容审查及发布说明；生产镜像构建、目标服务器验收和部署独立记录，尚未完成时在 Release 中明确标明。
5. 在通过源码验收的稳定分支提交上创建 `custom-v1.0.0` 和 GitHub Release。随后按 `VERSION` 构建镜像；镜像验证通过后记录摘要，并按摘要部署。
6. 发布后不移动标签、不覆盖已发布镜像对应内容；修复通过 1.0.1 发布。

第 19 期完成 Fork 及版本约定；第 20 期按用户授权执行首个 1.0.0 源码发布。源码发布、容器镜像交付和生产上线分别记录，不互相替代。
