# 第 06 期：表级权限策略基础

日期：2026-11-09。

## 需求与验收范围

确定业务角色如何向已具备数据库访问资格的用户附加单表权限，先交付独立的策略校验和计算模块，避免在尚未覆盖所有读取通道时启用限制性授权。该期不是完整权限矩阵上线。

## 设计决策

- 首批仅允许 table|read、record|read/create/update/delete。表结构、字段管理、导出、邀请等权限暂不纳入矩阵。
- 规则绑定业务角色 ID 与表 ID；同表同角色唯一。非空授权必须具备表和记录读取权限。
- 多角色权限取并集。保留现有手工协作者权限；撤销角色只撤销派生授权，不连带撤销独立权限。
- 必须已有数据库访问资格，且资源服务确认表属于目标数据库；矩阵不能单独创建数据库访问权。
- 仅普通用户身份使用本策略。分享、模板、机器人保留各自授权边界。策略非法或停用时不增加任何权限。
- 角色必须通过实时身份解析取得，客户端提供的角色或组织 Header 不可信。

## 实现

`apps/nestjs-backend/src/features/organization/authority-matrix/table-policy.ts` 提供严格策略校验和纯计算器；相邻 spec 覆盖跨库/表、身份模式、角色撤销、多角色合并、无效配置及越权操作。

## 尚未完成与下一期

当前模块没有接入 PermissionService，不影响在线权限，没有新增数据库迁移。下一期需要策略存储与并发版本控制、数据库管理员配置接口、替换原占位页面、实时角色解析和后端强制校验，并核查表权限 DTO、记录批量操作、导出/查询、实时订阅及 v2 入口的一致性。完成这些入口的验证前不能宣称矩阵完整可用。
